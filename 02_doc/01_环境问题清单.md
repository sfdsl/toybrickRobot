### P0-1 CH340G 在当前内核下不可用 —— 必须换方案 ✅ 已解决（2026-09-17）

现象：

```
内核配置：# CONFIG_USB_SERIAL_CH341 is not set
可用的（已内置 =y）：CONFIG_USB_SERIAL_CP210X=y、CONFIG_USB_SERIAL_FTDI_SIO=y
/lib/modules/5.10.160 下找不到任何 ch341 / usbserial 的 .ko 文件
modprobe ch341  →  FATAL: Module ch341 not found
```

即 CH340 驱动既没编进内核，也没有可加载模块，插上也不会出现 `/dev/ttyUSB*`。

三选一（推荐前两个）：

| 方案 | 做法 | 说明 |
|---|---|---|
| A（推荐·最省事） | 换用 **CP2102 或 FT232** 的 USB-TTL 模块 | 驱动已内置内核，即插即用 |
| B（推荐·嵌入式最佳） | 不用 USB，直连板载串口 `/dev/ttyS3` 或 `/dev/ttyS7`（电平需确认为 3.3V TTL） | 少一层转换，稳定性最好 |
| C | 重新编译内核打开 `CONFIG_USB_SERIAL_CH341=m` | 需 Toybrick 内核源码，风险最高，不优先 |

验证方法：插入模块后执行 `dmesg | tail -20`，应出现 `cp210x converter now attached to ttyUSB0`（或 `ftdi_sio`），并出现 `/dev/ttyUSB0`。

### P0-2 串口权限：当前用户不在 dialout 组

现象：

```
/dev/ttyS3   crw-rw---- root:dialout
用户组：toybrick, adm, sudo, video, input, render, netdev, docker   ← 缺 dialout
```

普通身份 `open('/dev/ttyUSB0')` 会 Permission denied，必须 sudo 才能跑。

解决：

```bash
sudo usermod -aG dialout toybrick
# 注销重新登录（或重启）后生效
groups   # 确认输出中含 dialout
```

已执行（2026-09-17）：`id toybrick` 输出含 `20(dialout)`；
用 `sg dialout -c 'stty -F /dev/ttyCH341USB0 115200 cs8 raw'` 验证普通用户可正常操作串口。
注意：已经打开的终端要执行 `newgrp dialout` 或重新登录才会生效。

状态：[x] 已解决

## 二、P1：计划缺口（必须补）

### P1-1 缺少轮式里程计 —— SLAM 的前置条件

底盘协议（取自 `02_doc/02_雷达和驱动板说明文档/大赛版 驱动板 - 操作说明.pdf`）要点：

- 控制：`AT+MT_SPWM=<A>,<B>,<C>,<D>`，值为 **-100~100 的 PWM 百分比**（**开环，无闭环调速**）
- 停止：`AT+MT_STOP`
- 编码器：`AT+MTENCODER?` → `+MOTORENCODER:<A>,<B>`，**文档注明"读取后计数值清零"**
- 转速：`AT+MTRPM?` → A/B 两路 r/m，每秒更新 10 次
- 另有 `AT+BATTERY?`、`AT+TEMPERATURE?`、`AT+HUMIDITY?`
- **无 IMU**（只有温湿度）

因此里程计必须自己做：

1. 固定频率（≥20Hz）轮询 `AT+MTENCODER?`，积分出 x / y / θ
2. 发布 `/odom`（`nav_msgs/Odometry`）+ `odom → base_link` 的 TF
3. 需标定：**轮径、轮距、每转脉冲数**
4. 注意"读取即清零"：**同一时刻只能有一个程序读串口**

状态：[x] 已完成（2026-09-18）：实现 + 真机验证 + 全部标定通过

实现：`ros2_ws/src/base_driver`（节点 `chassis_node.py`）——20Hz 轮询编码器、
差速积分、发布 `/odom` + `odom→base_link` TF；dry_run 冒烟测试通过；
真机初验通过（方向/符号全对，见《05_实验记录与结论.md》实验 1）。
标定完成（2026-09-18）：
- `ticks_per_meter = 3645`（实验 2：多次推车 2 米标定，复验误差 1.65%）
- `wheel_separation = 0.4085`（实验 3：转圈标定的**等效转向参数**；
  麦轮用差速里程计时该参数 ≈ 轴距+轮距+转向滑移修正，**非物理轮距**（0.2023）；
  转 180° 验证通过）
- 两参数均已写入节点默认值，可零参数启动
已知局限：驱动板只回 A/B 两路编码器（对应左右轮），横移时左右轮反向，
差速模型会把侧移误算为自转——横移工况的里程计不可信，后续若有 4 路编码器再升级。

### P1-2 串口独占导致的架构冲突

Qt 界面程序与 ROS 节点不能同时打开同一个串口。建议统一架构：

```
[Qt 界面] --(/cmd_vel)--> [底盘 ROS 节点(独占串口)] --(AT+MT_SPWM)--> 驱动板
                          [底盘 ROS 节点] <--(AT+MTENCODER?)
                              |
                            /odom + TF
```

- 底盘节点：订阅 `/cmd_vel` → 下发 PWM；定时读编码器 → 发布 `/odom` + TF
- Qt 界面：只发布 `/cmd_vel`，不碰串口
- 好处：步骤 2 写的界面在步骤 4 可直接复用，不用重写

状态：[x] 已按该架构落地（2026-09-17）

`base_driver` 节点独占串口；Qt 界面之后只需发布 `/cmd_vel`（不碰串口）。
另外节点启动时自动发一次 `AT+MT=ON,ON,ON,ON` 使能（见 P1-4）。

### P1-3 协议文档缺少串口参数 ✅ 已实测确认（2026-09-17）

PDF 共 5 页，**未写明波特率 / 数据位 / 停止位 / 校验位**。已用 `serial_probe.py` 实测：

- 波特率：**115200**
- 数据位 8 / 停止位 1 / 无校验（8N1，pyserial 默认参数即可）
- 指令结尾：`\r\n`（带回车换行；直接发 `AT` 即返回 `OK`）

实测响应格式（完整握手记录）：

```
>> AT                      << OK
>> AT+MTRPM?               << +MTRPM:\n0,0                （A/B 两路转速 r/m）
>> AT+MTENCODER?           << +MTENCODER:\n0,0            （A/B 两路计数，读取后清零）
>> AT+BATTERY?             << +BATTERY:\n12.691V,54mA,100%,3,0mAh
>> AT+TEMPERATURE?         << +TEMPERATURE:\n26℃          （GBK 编码，需容错解码）
>> AT+HUMIDITY?            << +HUMIDITY:\n52%
>> AT+MT_SPWM=20,20,20,20  << OK                          （运动指令同样有应答，便于确认）
>> AT+MT_STOP              << OK
```

注意点：

1. 温度值含 `℃` 符号且为 **GBK 编码**，UTF-8 解码会乱码，代码需 `utf-8 → gb18030` 容错
2. 查询类响应都是 **两行**（第一行 `+XXX:`，第二行数据），解析时应按行处理
3. `AT+MT_SPWM` 有 `OK` 应答，可据此确认指令被接收
4. 用串口助手手工测试时必须勾选"发送新行"（即指令结尾带 `\r\n`），否则驱动板无应答（2026-09-17 实测）

状态：[x] 已确认

### P1-4 运动控制的关键前置条件 ✅ 已从配套例程确认 + 实车验证（2026-09-17）

现象：`AT+MT_SPWM=20,20,20,20` 返回 `OK`，但**车轮不转**。
原因：**驱动板必须先收到电机使能指令**，否则 SPWM 指令只被接收、不输出。

实车验证（2026-09-17，串口助手 + 架空底盘）：
`AT+MT=ON,ON,ON,ON` → `AT+MT_SPWM=-80,-80,-80,-80` 发出后**四轮均向前**，
证明使能指令生效、负值=前进的方向定义正确。

`02_doc/01_51单片机控制底盘的代码例程` 是配套 51 例程（通过 uart4 控制驱动板），
从中确认了协议文档未写明的关键信息：

1. **必须先使能电机**：`AT+MT=ON,ON,ON,ON`
   （例程在 main 初始化时发一次；`AT+MT_STOP` 后建议重新发）
2. **PWM 正负定义与直觉相反**：
   - **负值 = 前进**：`AT+MT_SPWM=-80,-80,-80,-80`
   - **正值 = 后退**：`AT+MT_SPWM=80,80,80,80`
3. **通道分组**（由左转/右转/平移指令反推，待实测复核）：
   - A、C = 左侧轮；B、D = 右侧轮
   - 左转 `50,-50,50,-50`（左轮后退 + 右轮前进）；右转 `-50,50,-50,50`
   - 麦轮平移：左移 `40,-40,-40,40`、右移 `-40,40,40,-40`
4. **有效 PWM 幅度**：例程用 40~80（前进 80 / 低速 40 / 转向 50），
   20 可能低于电机启动死区
5. 例程开机还会发一条 `AT+EON`（注释"控制指令不返回OK"，用途待确认）

状态：[x] 已确认

### P1-5 colcon 构建 ament_python 包被"静默降级"，ros2 找不到包 ✅ 已解决（2026-09-17）

现象：`colcon build` 显示成功，但 `ros2 pkg executables base_driver` 报"包不存在"；
`colcon list` 显示包类型为 `(python)` 而不是 `(ros.ament_python)`。

根因链（逐层排查确认）：

1. `package.xml` 中 `<maintainer email="toybrick@localhost">` **邮箱不符合 RFC 格式**
2. catkin_pkg 解析 package.xml 失败 → colcon 无法把它识别为 ROS 包，**降级为普通 python 包**
3. 普通 python 包用基础 `PythonBuildTask` 构建，**跳过 ament 官方 hook 生成步骤**
4. 产物缺 `share/base_driver/hook/ament_prefix_path.sh` → 该包不会被加入 `AMENT_PREFIX_PATH`
5. 于是 `ros2 pkg` / `ros2 run` 找不到包（`source install/setup.bash` 只更新了 PYTHONPATH）

修复：邮箱改为合法格式（`toybrick@example.com`）后重建，hook 生成正常，
`ros2 pkg executables base_driver` → `base_driver chassis_node` ✓。

**教训：`package.xml` 的 email 必须带有效域名。`xxx@localhost` 这类写法不会中断构建，
只会静默降级，非常隐蔽。**（诊断命令：`colcon list` 看括号里的包类型）

顺带修复：本机 `ros2 topic` **全部子命令**不可用
（表面报 `KeyError: 'pub'`，实际是 `Failed to load entry point 'pub': No module named 'netifaces'`），
根因是 Rockchip 打包的 ros2cli 漏装依赖 **netifaces**。
修复：`pip3 install --user netifaces`（0.11.0 本地编译 aarch64 wheel 成功）。
修复后 `ros2 topic list/echo/pub` 全部正常。

状态：[x] 已解决

### P1-6 slam_toolbox 环境适配问题（TinyXML2 / empy / nav2_common）✅ 已解决（2026-09-20）

现象 1：CMake 报 `Could NOT find TinyXML2 (missing: TINYXML2_LIBRARY TINYXML2_INCLUDE_DIR)`。
根因：Rockchip 打包的 `tinyxml2_vendor` 只有查找脚本，系统缺真正的 tinyxml2 开发库。
修复：`sudo apt install libtinyxml2-dev`（2026-09-20 10:21 完成）。

现象 2：rosidl 生成接口时报 `AttributeError: module 'em' has no attribute 'BUFFERED_OPT'`。
根因：ROS 2 Foxy 的 rosidl 模板引擎要求 **empy 3.3.x**，而本机 `~/.local` 是 pip 装的
**empy 4.2.1**（4.x 删除了 `BUFFERED_OPT` 等旧接口）。
修复：`python3 -m pip install --user "empy==3.3.4"`（降级覆盖，不动系统）；
验证：`python3 -c "import em; print(hasattr(em,'BUFFERED_OPT'))"` → True。

现象 3：`ros2 launch slam_toolbox online_async_launch.py` 报
`ModuleNotFoundError: No module named 'nav2_common'`。
根因：官方 launch 文件用 `nav2_common.launch.HasNodeParams` 做"参数文件回退"检查，
Rockchip 打包无 nav2_common 包。
修复（本地适配补丁，src 与 install 已同步）：
- `online_async/sync_launch.py`：去掉 nav2_common 依赖，直接使用 params_file；
  `use_sim_time` 默认由 true 改为 false（真机无仿真时钟）
- `mapper_params_online_async.yaml`：`base_frame` 由 base_footprint 改为 **base_link**
  （本机 TF 链为 odom→base_link→base_laser，无 base_footprint）
- `mapper_params_online_async.yaml`：`map_update_interval` 5.0 → **1.0**（2026-09-20；
  原值使 `/map` 只有 0.2 Hz，实时看图太慢。注意该参数仅是**发布周期**，SLAM 实时性看 `map→odom` TF）
验证：启动成功——节点进程起、CeresSolver 插件加载、以 6Hz 接收 /scan；
2026-09-20 11:13 TF 四层完整（`map→odom` 由 SLAM 提供、`odom→base_link` 由底盘提供），进入建图（详见《05_实验记录与结论.md》实验 5）。

另注：**不要并发跑多个 colcon build**（同一 build/install 目录竞争会报
`INSTALL cannot copy file ... No such file or directory`；本次出现过一次，重跑即恢复）。

结果：slam_toolbox 构建成功（约 6.5 分钟；warning 为已知无害项），5 个可执行文件就位。
