## 一、小需求

| 项目 | 填写内容 |
|------|---------|
| **目标** | 用 ESP32-S3 开发板完成语音采集与播放，接入 xiaozhi 云端完成 ASR/LLM/TTS，并将云端返回的意图通过 MQTT 传递给 RK3588 执行导航动作。 |
| **输入** | 麦克风音频（Opus 编码）、云端意图文本。 |
| **输出** | MQTT 主题上的意图 JSON（`前进`/`去A区`/`停止`等）、TTS 语音播报。 |
| **业务规则** | 语音采集与网络通信走 Opus+UDP 保证实时性；意图指令走 MQTT 保证可靠；意图词汇表须为有限集合。 |
| **禁止行为** | **不得上传音频原始数据到非授权服务器**；不得将 MQTT 指令直接转化为电机驱动（须由 RK3588 行为树校验）。 |
| **边界条件** | 网络中断、云端超时、唤醒词误触发、意图词汇表外的话语。 |
| **验收标准** | 离线唤醒词识别率 ≥ 90%；云端断连时本地意图词仍可触发停车；5 个标准指令识别正确率 ≥ 85%。 |
| **风险区域** | 云端断链、明文传输、音频数据合规。 |

## 二、小计划

### 方案 A：xiaozhi-esp32 官方固件 + 自建意图桥接（推荐）

- **做法**：刷官方固件完成 ASR/LLM/TTS 链路，自建 MQTT 桥接节点解析意图。
- **复杂度**：中。
- **维护成本**：中。
- **风险**：官方固件定制能力有限，需确认意图词如何回传。
- **依赖**：`xiaozhi-esp32` 固件、MQTT Broker。
- **适用场景**：快速验证语音链路。

### 方案 B：自建 ESP32 语音固件

- **做法**：用 ESP-SR 或第三方库在 ESP32 上完成唤醒词与 ASR。
- **复杂度**：高。
- **风险**：中文 ASR 在 ESP32 上资源紧张，识别率难以保证。
- **适用场景**：对云端依赖有严格限制。

### 方案 C：RK3588 直接跑语音（单板方案，备选）

- **做法**：语音采集与云端推理全在 RK3588 完成。
- **复杂度**：中。
- **风险**：与 SLAM/Nav2 抢占算力，无低功耗待机。
- **适用场景**：作为对照基线。

### 选定方案与理由

**选定**：方案 A

**理由**：xiaozhi-esp32 已完成 Opus+UDP 音频链路与 MCP 工具调用，自研部分仅聚焦意图解析与桥接，工作量可控。
