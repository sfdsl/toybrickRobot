## 一、小需求

| 项目 | 填写内容 |
|------|---------|
| **目标** | 存储小车位姿遥测与轨迹点位，通过空间查询回答"路过哪些地点""做过哪些事"。 |
| **输入** | 位姿遥测流（timestamp、position、orientation、battery 等）。 |
| **输出** | 到访事件表、轨迹查询接口、任务与告警记录。 |
| **业务规则** | 位姿写入走 TimescaleDB 自动分区；空间查询走 PostGIS；坐标基准必须统一且带注释。 |
| **禁止行为** | **不得删除历史数据**；不得修改既有表结构；不得将坐标数据用于未授权的第三方服务。 |
| **边界条件** | 时间戳乱序、坐标跳变（GPS 漂移类异常）、重复点位、表膨胀。 |
| **验收标准** | "某点位 5m 内所有位姿"查询 ≤ 100ms（百万行）；到访事件无重复；轨迹回放数据完整。 |
| **风险区域** | **坐标基准错误导致空间查询失准、表膨胀、历史数据误删**。 |

## 二、小计划

### 方案 A：PostgreSQL + PostGIS + TimescaleDB（推荐）

- **做法**：PostGIS 存轨迹点位与 POI，TimescaleDB 存时序遥测，普通表存任务与告警。
- **复杂度**：中。
- **维护成本**：中。
- **风险**：坐标基准需在入库前统一；VACUUM 需配置。
- **依赖**：`postgresql-15`、`postgis`、`timescaledb`、`pgbouncer`。
- **适用场景**：本项目全场景覆盖。

### 方案 B：仅 TimescaleDB

- **做法**：只用时序库存点位，空间查询在应用层做。
- **复杂度**：低。
- **风险**：空间查询能力弱，到访判断需全表扫描。
- **适用场景**：只需存，不做空间分析。

### 方案 C：IoTDB + 应用层空间索引

- **做法**：国产时序库存数据，应用层自建空间索引。
- **复杂度**：高。
- **风险**：空间查询实现复杂，维护成本高。
- **适用场景**：有国产化硬性要求时。

### 选定方案与理由

**选定**：方案 A

**理由**：PostGIS 是 OGC 空间标准的实现，`ST_DWithin` 可直接完成"5m 内点位"查询，百万行毫秒级；TimescaleDB 自动分区降低运维负担。
