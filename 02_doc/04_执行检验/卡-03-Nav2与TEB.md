## 一、小需求

| 项目 | 填写内容 |
|------|---------|
| **目标** | 完成 Nav2 导航栈集成，局部控制器采用 **`RotationShimController` 包裹的 `MPPIController`**，使小车能在建好的地图内自主移动到指定目标点并避开静态/动态障碍物。 |
| **输入** | `/map`、`/odom`（滤波后）、`/scan`、`/tf`、目标点 `/goal_pose`。 |
| **输出** | `/cmd_vel`（线速度与角速度）。 |
| **业务规则** | `SmacPlanner2D` 出全局路径 → `MPPI` 做局部轨迹优化（critic 加权）；**MPPI 参数须按实车约束填写**（`max_vel_x`、`max_vel_theta`、footprint、`wz_max`）。 |
| **禁止行为** | **VLA 或其他高层模块不得绕过代价地图直接写入 `/cmd_vel`**；不得关闭代价地图的障碍物层；**不得让 nav2 发 `vy`**——底盘虽是麦轮，但 `/odom` 是差速积分（只有左右轮编码器），横移时里程计不可信，**nav2 必须配差速模型**。 |
| **边界条件** | 目标点在障碍物内、目标点超出地图、定位丢失、机器人被卡住（局部最小值）。 |
| **验收标准** | 10m×10m 环境内，5 个随机目标点，成功率 ≥ 80%；通过 80cm 宽通道时不碰壁。 |
| **风险区域** | ① **摆头/蛇行**（P26/P27 实测：`RotationShim` 与"BT 每秒重规划"结构性冲突，表现为 `v=0` 纯转且 ω 满幅）；② **底盘 ω/v 死区**（低速解磨蹭，已由 `wz_boost=0.18` / `vx_boost=0.07` 补偿）；③ **差速不能倒车**（`min_vel_x=0`，卡住时只能转身）；④ **`inflation_radius` 必须 ≥ `collision_monitor` 的 PolygonStop 距离**，否则互相打架（P3 实测死锁）；⑤ 局部最小值（U 型）；⑥ **到达判据与目标朝向冲突（P35，2026-10-19 已修）**：手机 `set_goal` 写死 `orientation.w=1.0` → 目标朝向恒为 0°；车从对侧到达时车头 ≈180°，实测差 **153.5°**，而 `yaw_goal_tolerance` 原为 0.50（≈29°）→ goal checker **永不判到达** → 控制器在目标点原地小幅来回拧（v≈0，ω 在 ±0.1~0.3 抖动），再被底盘 `wz_boost`(0.15→0.18) 放大成肉眼可见的"转圈"，而 nav2 日志里**一条错误都没有**。已放宽到 **3.15（≈181°）= 只判位置**，与 P22 本意一致。⚙️ 若以后要让车到点后朝向某方向，应改 `set_goal` 发真实 yaw，**不要**靠收紧这里；⑦ **接近目标时磨蹭/反复修正位姿（P36，2026-10-19 已修）**：`GoalAngleCritic`(权重 1.5) 会惩罚车头与"目标朝向"的偏差，而手机 `set_goal` 写死 `yaw=0`、车到点朝向任意 → 该 critic 在为**虚构目标**付出代价，与"走到点上"互相拉扯 → 最后 0.5 m 反复修正；再被底盘 `wz_boost`(0.15→0.18) 放大成可见抖动。已 **`GoalAngleCritic.enabled: False`**（配合 `yaw_goal_tolerance: 3.15` 只判位置）。⚙️ 另：**末段减速（P37，2026-10-19 已改）**——`GoalCritic.threshold_to_consider` 0.5→**0.25**。机制：该 critic 在 `goal_dist <= 阈值` 时生效，按轨迹各点到目标的距离打分；而 MPPI 时域 = `time_steps(12) × model_dt(0.25)` = **3 s**，全速 0.2 m/s 时覆盖 0.6 m → 进入 0.5 m 后冲过头会涨代价 → 优化器按"剩余距离/3 s"自动配速（0.5 m≈0.17 → 0.25 m≈0.08 → 0.1 m≈0.03），体感"不干脆"。降到 0.25 后只在最后 25 cm 配速；`xy_goal_tolerance=0.20` 会锁存，轻微冲过头不影响判到达。若仍偏慢，下一个杠杆是 `GoalCritic.cost_weight` 5.0→3.0。 |

## 二、小计划

### 初版三个候选（2026-09 制定，**已被实测取代，保留作记录**）

#### 候选 A：Nav2 + TEB（初版推荐）
- **做法**：`teb_local_planner`，图优化同时求解空间与时间。
- **复杂度**：中，参数较多。**风险**：参数未校准易贴墙/抖动；计算量需控制优化窗口。
- **适用场景**：差速/阿克曼、狭窄或障碍密集。

#### 候选 B：Nav2 + DWA
- **做法**：动态窗口法。**复杂度**：低。
- **风险**：狭窄通道通过性弱于 TEB，无时间最优。
- **适用场景**：开阔环境、快速跑通基线。

#### 候选 C：纯追踪（仅路径跟随）
- **做法**：只跟随路径，不做局部避障。
- **风险**：无法处理动态障碍物，不符合本项目避障需求。

### 实际走过的路线（P2~P32，详见 `12_导航精度调优记录.md`）

| 阶段 | 控制器 | 结果 |
|---|---|---|
| P2~P10 | `RegulatedPurePursuitController` | 与自研纯跟踪同族、参数少，用于对齐基线 |

### 为什么不用 TEB（本卡最重要的结论）

**结论：从未评估，也从未安装。** 证据：

- `teb_local_planner` 在 `/opt/ros/humble` 与 `~/RobotCode/ros2_ws/install` 下**都不存在**
- `08_nav2_自主导航方案.md`、`12_导航精度调优记录.md`、`nav2_params.yaml` 全文 **0 次**提及 TEB
- `08` 的 §2.2 选型清单只有三个候选：**RPP / DWB / MPPI，没有 TEB**

初版选 TEB 的理由是"林道 = 狭窄 + 有障碍 + 需平滑"，但实际场景是 **10m×10m 室内、80cm 通道**，不在 TEB 的强项区间。逐条对比：

| 维度 | TEB | MPPI | 对本车的意义 |
|---|---|---|---|
| 数学本质 | 稀疏图优化（梯度法） | 采样 + 加权平均（无梯度） | 采样法不依赖代价可微，非凸的室内 costmap 更友好 |
| 约束 | **硬约束**，不可行解不产生 | **软约束**，折成 critic 代价 | 本车差速约束简单，硬约束优势体现不出来 |
| 时间维度 | 每段 ΔT 是优化变量 → **时间最优** | 固定 N×dt | 本项目无到达时限，用不上 |
| 局部极小 | 梯度法易陷（U 型死角典型） | 采样有多样性，跳出能力更好 | MPPI 更抗死角 |
| 全向能力 | 可配 holonomic | 可配 Omni | **两者都用不上**：`/odom` 是差速积分 → 必须配差速 |
| 计算 | 随优化节点数增长，单次迭代重 | K×N 批量前推，xtensor 向量化 | RK3588 上 **MPPI 实测 4 Hz**；TEB 无实测数据 |
| 生态 | ROS1 时代经典，ROS2 维护较弱 | nav2 官方主推，Humble 自带 | MPPI 文档/示例更全 |

**不选 TEB 的三条决定性理由**：

1. **算力未验证**。MPPI 在 RK3588 上已实测 4 Hz 跑得动；TEB 没有实测数据，验收前引入未知风险不划算。
2. **已投入的调参不可复用**。MPPI 走完了 P11~P32（含与底盘 `wz_boost` 死区补偿的联动），换 TEB 等于全部作废重来。
3. **换 TEB 解决不了已踩的坑**。P26/P27 的摆头根因是 `RotationShim` 与"BT 每秒重规划"的结构性冲突（车头与新路径起始方向反复差 >45° → shim 猛转并过冲），属**行为树重规划频率**问题，与局部规划器算法无关。

**TEB 的优势场景（留给以后的判断依据）**：狭窄且障碍密集、需要连续距离场精修贴边；有到达时限需时间最优；阿克曼车需硬转弯半径保证。

### 选定方案与理由

**选定**：Nav2 + `RotationShimController`(MPPI)，DWB 备用。

**理由**：MPPI 的软约束 + 采样多样性更适配非凸的室内代价地图，且已在 RK3588 上验证满足实时性；shim 只负责"起步/大偏差时先摆正"，其余交给 MPPI。回退路径完整（`FollowPath` ↔ `FollowPathDWB` 键名互换）。
